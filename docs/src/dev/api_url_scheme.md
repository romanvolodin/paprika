# Схема адресов REST API

Здесь описано, как устроены адреса REST API Паприки. Добавляете новый адрес? Сначала сверьтесь с принципами ниже, чтобы он выглядел так же, как остальные.

## Общие принципы

- Префикс `/api/v1/` у всех адресов.
- Имена ресурсов — во множественном числе. Составные — в kebab-case (`shot-groups`, `shot-tasks`, `task-types`).
- Все адреса заканчиваются косой чертой.
- **Гибридная схема:**
  - list и create идут через родителя;
  - retrieve, update и delete — по прямому адресу, по собственному id ресурса.

Как это выглядит на примере проектов:

```txt
GET /api/v1/companies/<id>/projects/    # список проектов компании
GET /api/v1/projects/<id>/              # один проект
```

Правило простое. Чтобы получить список или создать объект, нужен родитель. Чтобы работать с уже существующим объектом, хватает его id, и тащить за собой всю цепочку родителей не нужно.

## Дерево адресов

Дерево будет дополняться.

```txt
# Company
GET/POST         /api/v1/companies/
GET/PATCH/DELETE /api/v1/companies/<id>/

# TaskType и TaskStatus принадлежат компании
GET/POST         /api/v1/companies/<id>/task-types/
GET/PATCH/DELETE /api/v1/task-types/<id>/
GET/POST         /api/v1/companies/<id>/task-statuses/
GET/PATCH/DELETE /api/v1/task-statuses/<id>/

# Project принадлежит компании
GET/POST         /api/v1/companies/<id>/projects/
GET/PATCH/DELETE /api/v1/projects/<id>/

# ShotGroup принадлежит проекту
GET/POST         /api/v1/projects/<id>/shot-groups/
GET/PATCH/DELETE /api/v1/shot-groups/<id>/

# Shot принадлежит группе
GET/POST         /api/v1/shot-groups/<id>/shots/
# Список кадров проекта
GET              /api/v1/projects/<id>/shots/
# Значения, по которым можно фильтровать кадры проекта: только реально встречающиеся
GET              /api/v1/projects/<id>/shot-filters/
GET/PATCH/DELETE /api/v1/shots/<id>/
# Импорт кадров из таблицы: много кадров за один запрос (см. ниже)
POST             /api/v1/projects/<id>/shot-imports/

# Task принадлежит проекту. Может существовать без кадров (самостоятельная
# задача) и привязываться к нескольким кадрам через ShotTask
GET/POST         /api/v1/projects/<id>/tasks/
GET/PATCH/DELETE /api/v1/tasks/<id>/

# ShotTask — привязка Task к кадру. Здесь же хранится работа над задачей на
# этом кадре: статус, исполнитель, оценочное и фактическое время (в часах).
# POST принимает task_id существующей задачи того же проекта; новая задача
# на кадр — это два запроса (создать Task, затем привязать)
GET/POST         /api/v1/shots/<id>/tasks/
GET/PATCH/DELETE /api/v1/shot-tasks/<id>/

# Version принадлежит кадру. Версию нельзя изменить или переименовать:
# ошибочную удаляют и загружают заново (поэтому нет PATCH)
GET/POST         /api/v1/shots/<id>/versions/
GET/DELETE       /api/v1/versions/<id>/

# Chat принадлежит кадру
GET/POST         /api/v1/shots/<id>/chat/
GET/PATCH/DELETE /api/v1/chat/<id>/

# Feed только собирает и отдаёт события за последнее время,
# адреса для создания нет
GET              /api/v1/projects/<id>/feed/
```

## Параметры списков

Базовые параметры:

- `page` — номер страницы, начинается с 1.
- `page_size` — размер страницы. По умолчанию 20, максимум 100.
- `search` — поиск `icontains` по паре текстовых полей.

Ответ приходит в виде `{items, total, page, page_size}`.

Новые списки делаем так же, если нет причины отклониться.

### Где список отличается

- **Shots.** `page_size` до 500 (в остальных списках максимум 100): на странице кадров пользователь сам выбирает размер страницы. Есть дополнительные фильтры:
  - `task_type=<id типа задачи>` — кадры, у которых есть хотя бы одна задача этого типа. Работает в обоих списках кадров;
  - `status=<id>,<id>` — кадры с одним из перечисленных статусов. Работает в обоих списках кадров;
  - `assigned_to=<user_id>,<user_id>,none` — кадры, у которых есть ShotTask, назначенный на одного из перечисленных пользователей. `none` — ShotTask без исполнителя. Работает в обоих списках кадров. Значение `me` пока не поддерживается.
  - каждый кадр приходит с `thumb`: адресом превью его последней версии. Если версий нет или у последней нет превью, `thumb` равен `null`.
- **Tasks.** Базовые параметры (`search` ищет по названию и коду) плюс `type=<id типа задачи>`. Новые сверху.
- **ShotTask** (`GET /shots/<id>/tasks/`). Без пагинации: список отдаётся целиком, в порядке создания. На кадре задач единицы. Каждый элемент — данные ShotTask и вложенная задача.
- **Versions.** Только базовые параметры.
- **Chat.** Курсорная пагинация вместо `page` и `page_size`:
  - `limit` — по умолчанию 50;
  - `before=<message_id>` — подгрузить более старые сообщения.

  Первый запрос без `before` возвращает последние `limit` сообщений в хронологическом порядке.

- **TaskType**, **TaskStatus.** Без пагинации, список отдаётся целиком (опционально с `search`).
- **Feed.** Пока собирает события из таблиц chat, task и version. Отдельная таблица лога появится позже.

  Ответ — `{items, next_before_date}`, новые события сверху. Один ответ покрывает 5 дней, считая от самого нового найденного события, поэтому тихая неделя не даёт пустую страницу. Чтобы подгрузить более ранние события, значение `next_before_date` передают в `before_date`. Когда старше ничего нет, `next_before_date` равен `null`.

  Три типа событий:
  - `chat` — сообщение пользователя (удалённые не попадают);
  - `version` — загруженная версия;
  - `task` — задача добавлена на кадр, сменился статус или исполнитель. Это системные сообщения чата кадра. Сообщения о загрузке версий пропускаются, потому что сами версии уже есть в ленте.

  Фильтры:
  - `type=chat,task,version` — по умолчанию все типы;
  - `mine=true` — только события по кадрам, у которых есть ShotTask, назначенный на пользователя;
  - `before_date=` — курсор подгрузки (дата и время).

  Фильтры `created_by`, `date_from` и `date_to` пока не реализованы.

## Загрузка файлов

Как загружать файлы, зависит от того, сколько их у ресурса: один или много.

### Один файл на ресурс

Так работают аватар пользователя и обложка проекта. Файл идёт через `multipart/form-data` прямо в теле `POST` или `PATCH` самого ресурса, вместе с остальными полями.

### Версия

Версия — это один файл, поэтому создаётся как аватар: `multipart/form-data` в теле `POST /shots/<id>/versions/` с обязательным полем `source`.

- Имя версии берётся из имени файла без расширения. Оно должно быть уникальным в проекте.
- Метаданные и превью создаются в рамках этого же запроса.
- Прогресс загрузки показывает клиент (axios `onUploadProgress`).
- Несколько версий с одним комментарием загружаются отдельными запросами. Комментарий потом создаётся сообщением чата, привязанным к нескольким версиям.

### Ресурс со множеством файлов

Так работают вложения в чат. Нужен отдельный адрес загрузки, не связанный с ещё не существующим родителем:

```txt
POST /shots/<id>/chat/attachments/   → {id, url, filename, size, content_type}
POST /shots/<id>/chat/               → {text, attachment_ids: [1, 2]}
```

Сначала грузим файлы и получаем их id. Потом создаём сообщение со списком id.

Что это даёт:

- прогресс и перезапуск загрузки (при необходимости) по каждому файлу отдельно;
- возможность убрать файл до отправки сообщения.

### Массовое создание кадров

Кадры из таблицы Excel или Calc создаются одним запросом `POST /projects/<id>/shot-imports/`. Это отдельный адрес, а не `POST /projects/<id>/shots/` со списком в теле: тот создаёт один кадр и устроен под него.

Таблицу читает клиент прямо в браузере. Сервер файла не видит и не хранит, ему приходит готовый список кадров:

```json
{
  "shots": [
    {
      "name": "VRG_01_0150",
      "rec_timecode": 4000,
      "groups": ["01 СЕРИЯ"],
      "tasks": [{"task_id": 7}, {"name": "Вставка в монитор", "type_id": 3}],
      "messages": ["Текст задачи", "Комментарий продюсера"]
    }
  ]
}
```

- **Группы** передаются именами. Группы с таким именем в проекте нет — она создаётся.
- **Задачи** бывают двух видов: существующая (`task_id`) или новая (`name` и `type_id`). Одна и та же новая задача у нескольких кадров создаётся один раз.
- **Сообщения** попадают в чат кадра обычными сообщениями от имени того, кто импортирует, в том порядке, в котором лежат в списке. Системные события «задача добавлена» при импорте не создаются.
- Все кадры получают статус по умолчанию, у задач на кадрах тоже статус по умолчанию.
- Длительность не передаётся: она появится позже, с нулевой версией из монтажа.
- За раз можно создать не больше 2000 кадров (`SHOT_IMPORT_MAX_ROWS`).

Запрос выполняется целиком или не выполняется совсем: одна транзакция. Если хотя бы со строкой что-то не так, не создаётся ничего. Ответ `400` перечисляет все проблемы сразу, а в `loc` каждой указано место: `["shots", 3, "name"]` — имя кадра в четвёртой строке списка. Так клиент подсвечивает строки на странице предпросмотра.

## WebSocket-адреса

Префикс — `/ws/v1/`. Конкретные пути пока не определены.

## Формат ошибок и статус-коды

Пока не решено:

- единый формат тела ошибки (`{"detail": ...}` или `{"errors": [...]}`);
- 404 или 403 для чужого проекта.
